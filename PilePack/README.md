# PilePack — сборка `gamedataNN.pile` из `Data/`

Кросс-платформенная (Python 3.8+, без зависимостей) замена `FilePileCompiler.exe` +
`PW_PackData/FilePileCompiler/process_data_pile.py`. Один проход по `Data/` вместо
шести прогонов компилятора с ручным перемещением файлов в `_processedFiles`.

Запуск из корня репозитория: `./pilepack.sh plan`, `./pilepack.sh build` (Windows —
`pilepack.cmd`). Готовые контейнеры — в `Piles/` (в `.gitignore`).

---

## 1. Требования (постановка)

1. Имена контейнеров — `gamedata01.pile`, `gamedata02.pile`, …
2. Каждый pile привязан к **фиксированному списку файлов**, зафиксированному при первом
   прогоне:
   - список «дорастает» до целевого размера, дальше открывается новый pile;
   - изменился файл — пересобирается **только его** pile;
   - новые файлы попадают в **последний** pile, ещё не достигший целевого размера;
   - файл удалён из `Data` — он **остаётся закреплён** за своим pile, но уходит из него
     и обратно не возвращается;
   - если pile при пересборке переваливает за порог — его список делится **по байтам**
     на равные части: первая остаётся под старым именем, вторая получает следующий
     свободный номер (имена остальных pile не меняются).
3. Скрипт сам исследует `Data/` и пересобирает только реально изменившиеся pile.
4. Логика формата повторяет `FilePileCompiler`, скрипт кросс-платформенный и не медленнее
   оригинала.
5. Старые pile удаляет апдейтер (в `pwc-gitupdates` `*.pile` не в `.gitignore` →
   `git reset --hard` + удаление untracked в NanoUpdater их снимает).
6. `fsb` (и `fev`) кладём в pile — унификация, исключений для аудио не делаем.

Решения заказчика: целевой размер **50 МБ** (не 70), делить **по байтам**, манифест в
**исходном репо**, уровень zlib **6** допустим, локализация **не хранится отдельно**
(унификация), история чистится периодически.

С 2026-10-21 целевой размер — **20 МБ** (~100 pile вместо 44): правка одного файла
переписывает в канале обновлений весь его pile, и мелкие pile меньше раздувают историю.

Источник истины — **текущая `Data/`**. Существующие pile никуда не распаковываются и
не сливаются с `Data` (решение 2026-10-19). Чем это грозит контентно —
`docs/DATA_VS_PILES_REPORT.md` (450 файлов, существующих только в каналах обновлений,
из новой сборки не попадут в pile; 426 МБ `Data/Audio` останутся отдельными файлами).

## 2. Формат (повторен побайтово)

Формат описан в `pw/branches/r1117/Src/System/FileSystem/FilePileFormat.h`, читается
`FilePileLoader::Init` (`Src/System/FileSystem/FilePileLoader.cpp`).

```
[0]     tag 'Pile' (0x656c6950)
[4..]   блоки данных файлов (первый — со смещения 4)
        строковая таблица: имена с terminating zero
        индекс: N × SFilePileEntry <6I: size, sourceSize, offset, flags,
                fileNameOffset, crc>            — обфусцирован SimpleCrypt
        хвост: SFilePileTail <6I: tag, version=0x00010002, filesNumber,
               stringsOffset, stringsLength, fileIndexOffset> — НЕ обфусцирован
```

* Обфускация (`Src/System/SimpleCrypt.hpp`): `state = 0`; на каждый байт
  `state = (state + 83) & 0xFF; out = b ^ state`.
* `crc` — `zlib crc32` **несжатых** байт.
* Сжатие: `zlib level` (по умолчанию 6), если `сжатый размер ≤ ratio × исходного`
  (ratio 0.90) и исходный размер > `min_file_to_compress` (1) — ставим флаг
  `FILEPILE_COMPRESSED (0x0001)`, иначе пишем как есть и флаг не ставим.
  Проверка «не сжалось» нужна не только ради размера: `FilePileLoader::ReadFileBytes`
  для сжатой записи делает `DecompressFile` и, если тот вернул false, читает байты как
  есть, а `CheckCrc` сверяется с **несжатыми** данными — запись, где блок не декомпрессируется,
  стала бы битой.
* Имена в pile — с `/` (Windows-разделитель тоже принимается загрузчиком,
  `FilePileLoader::Init:101`), ключ поиска — `strlwr(имя)` (`PileFileSystem.cpp:139`).

Лимиты (проверяются на сборке): `size`/`sourceSize` < `fs_piled_file_size_limit` (256 МБ),
смещения — `UInt32`, то есть pile < 4 ГБ, но сам `FilePileCompiler` останавливается на
`0x7FFFFFFF` (2 ГБ, `FilePileCompiler.cpp`); загрузчик требует `0 < filesNumber < 1 048 576`
и `stringsLength < 16 МБ` (`FilePileLoader::Init`).

**Почему нельзя «просто положить всё подряд»:** `FilePileLoader::Init` возвращает false при
любом имени записи, начинающемся с `'0'` или `'/'` (`FilePileLoader.cpp:101`), а
`PileFileSystem::ScanForPiles` при неудачном `Init` **молча** пропускает контейнер
(колбэк `OnPileOpenFailed` закомментирован, `PileFileSystem.cpp:102`). Один файл вида
`00000000000000000000000000000000` (в `Data` такие есть — `Maps/multiplayer/moba/__b3a9…road`)
обрулил бы `Init` всего контейнера, и его содержимое исчезло бы без единой строчки в логе.
Отсюда проверки в `build_pile` и `verify`.

## 3. Отбор файлов (`policy.txt`)

`policy.txt` рядом со скриптом: `ext:` (разрешённые расширения), `ignore_dir:`
(каталоги целиком), `exclude:` (fnmatch; маска без `/` сравнивается с именем файла, с `/` —
с полным относительным путём от `Data`; `!`-префикс снимает прежнее исключение, правила
применяются по порядку, последнее совпадение важнее). По умолчанию — расширения старого
`types.txt` **плюс** `txt`, `fsb`, `fev`;
исключены `.svn`, `Debug`, `Templates`, `Test`, `_processedFiles`, `deprecated_shaders`,
`*.junk`, `*.ignore` и нерусские голосовые банки (`audio/asks0*_EN_TR.fsb` и т. п. —
`PackData.ps1` исключал `*_DE*/*_EN*/*_FR*/*_TR*`).

**Ссылки в исключённые каталоги.** `ignore_dir` не абсолютен: файлы из исключённых каталогов,
на которые ссылаются отобранные `.xdb` (прямо или через другие такие файлы), всё равно идут в
pile, если проходят `ext` и `exclude`. Ссылки — `href="…"` (без расширения — `.xdb`),
`textref="…"` и пути в тексте тегов (`<geometryFileName>/Maps/x.stat</geometryFileName>`); к `.txt`
добавляется перевод `<имя>_en.txt`. Без этого живые данные ссылались в пустоту, и клиент падал:
тестовый глиф `Maps/Test/PlaneMap/GiftGlyph/PrimeRune.GLPH` стоит в общем `Glyphs/_.GLDB`
(падение в `AdventureScreen::PrecacheResources`), на `Maps/Test` ссылаются порталы и спавнер
основной MOBA, эффекты свитков (`Effects/Test/Scroll`), `Tech/Default/_.MAPLST` (падение в
`SelectGameModeScreen`). В 2026-10 так добавляется ~390 файлов (~60 МБ исходников, в основном
тестовые карты из списков карт). В логе сборки — «из них N из игнорируемых каталогов».

Локализация (`Data/Localization/**`) больше не исключается: она собирается в общий набор
(унификация). Разделитель пути в ключах — `/`, ключ регистронезависим.

⚠ Следствие унификации: `PileFileSystem` перекрывает `Data/` (`Game.cpp:1177` — pile-ФС
регистрируется раньше файлового), поэтому любой файл из `Data`, попавший в pile, перестаёт
читаться «как есть». Явно это заметно на `Data/Localization/**` (см. риск R3 в плане) и на
`Data/Audio/*.fsb` (читаются из pile, а не с диска).

## 4. Манифест привязки

`PilePack/gamedata_manifest.json` (в репозитории, коммитится). Схема v1:

```json
{"format": 2, "params": {"target_bytes": 52428800, "split_bytes": 62914560,
 "level": 6, "max_ratio": 0.9, "min_compress_size": 1, "prefix": "gamedata",
 "policy_fingerprint": "…"},
 "piles": [{"id": 1, "name": "gamedata01.pile", "packed_size": 51900000,
            "files": [["audio/ambient.fsb", 8577152, 2711085373], …]}]}
```

Запись о файле — `[ключ, размер, crc32]`. В формате 1 был ещё `mtime_ns` (4-е поле) —
убран: он нужен был только для ленивого пересчёта crc, а правку «тот же размер, другие
байты» всё равно не ловил. Формат 1 читается (лишнее поле отбрасывается), пишется формат 2.
**crc считается у всех файлов каждый прогон** — на всю `Data` ~7 с, и только это надёжный
признак изменения.

Правила пересборки (`cmd_build`):

* **новые** файлы → в последний pile с `packed_size < target` (если такого нет — новый pile);
* **изменились** (размер или crc не совпали) → помечается pile-владелец;
* **удалены** из `Data` → запись остаётся в pile, но помечается pile на пересборку, и при
  пересборке запись выпадает (обратно не вернётся: в `Data` файла нет);
* **битый/недостающий** файл в pile → пересборка: индекс на диске сверяется с манифестом
  (`disk_matches` — набор ключей + исходные размеры), рассогласование чинится само;
* пересобраиваемый pile по фактическому размеру > `split` (30 МБ при цели 20) → его список
  делится **по исходным байтам** пополам (граница — где накопленная сумма дошла до
  половины), каждая часть — отдельный pile; деление повторяется, пока все части не
  окажутся ниже порога (или пока в части не останется один файл);
* **имена стабильны**: первая часть остаётся под старым именем, вторая получает номер
  после максимального (дыры не переиспользуются). Раньше имена пересчитывались по порядку,
  и после деления одного pile «менялись» все следующие — в git и в канале обновлений это
  десятки изменённых файлов без изменений данных.

Порог деления по умолчанию = `target + 10 МБ` (30 МБ при цели 20 МБ). В исходной
постановке было «переваливает за 95 МБ» — при цели 50 МБ это дало бы куски 95–190 МБ,
поэтому порог привязан к цели. Меняется `--split`.

`--force` пересобирает всё. Смена любого параметра сборки или `policy.txt` (его sha256
хранится в манифесте) тоже переводит сборку в полный режим.

**Смена цели** (`--target` не совпал с `target_bytes` в манифесте) или `--relayout` —
раскладка с нуля: все файлы раскладываются по новым pile с номерами с 001 (не меньше трёх
цифр, `NAME_DIGITS`: `ScanForPiles` сравнивает имена как строки, и при двух цифрах
`gamedata100` оказался бы «меньше» `gamedata99`), старые pile из `Piles/` удаляются. Делить старые pile пополам было бы
неправильно: из 50 МБ получились бы половинки по 25, а не 20. После раскладки заново
каналу обновлений нужна полная перезаливка pile.

**Переводы строк.** Git хранит текстовые файлы `Data` (`.xdb`, `.lua`, `.tcv_data`,
`.hlsl`) с LF, а на диске они в CRLF или LF в зависимости от `core.autocrlf` клона.
Скан и упаковка приводят текст к LF (`canon()`); текст от двоичного отличается по
эвристике git (`convert_is_binary`: NUL, одиночный CR, много непечатаемых байт —
двоичный, его байты не трогаются). Без этого сборка из клона с другим `autocrlf`
пересобирала 38 pile из 44, а снаружи это выглядело как «индекс на диске не совпадает
с манифестом» почти у всех pile (перед этой проверкой в записи подставляются текущие
размеры из `Data`, так что сообщение значит «изменились исходники»).

## 5. Команды

```
./pilepack.sh plan                        — сверка манифеста, план, ничего не пишет
./pilepack.sh build  [--force] [--relayout] [-j N] [--keep-stale]
./pilepack.sh verify [--fast]             — структура + crc всех записей + лимиты загрузчика
                                            + сверка Piles/ с манифестом
./pilepack.sh status                      — сводка по манифесту
./pilepack.sh extract <pile> [ключ…] [--to файл|-]  — список записей / выгрузка файла
./pilepack.sh clean                       — удалить все pile из Piles/
```

Ключи сборки: `--data <каталог>` (по умолчанию `pw/branches/r1117/Data` относительно
репозитория), `--out <каталог>` (по умолчанию `Piles/` в корне репо), `--manifest`,
`--policy`, `--target <байт>` (20MB), `--split <байт>` (target + 10MB), `--level <0-9>` (6),
`--ratio` (0.90), `--min-cs` (1), `--est-ratio` (0.50 — оценка упакованного размера при
первой раскладке), `--prefix` (`gamedata`), `-j/--jobs` (`min(4, cpu-1)`), `--force`,
`--relayout` (разложить файлы по pile заново), `--keep-stale`.

## 6. Скорость (замеры на реальной `Data`)

Однопроходный скан `Data` (crc считается у всех файлов — другого надёжного признака
изменения нет), сжатие и crc — в пуле процессов (`--jobs`), крупные файлы читаются через
`mmap`.

Выборка 120 МБ: `zlib.crc32` 1964 МБ/с, level 9 — 12,2 МБ/с (коэффициент 0,531),
level 6 — 38,9 МБ/с (0,533, размер больше на 0,4 %) — отсюда level 6 по умолчанию.

Полный прогон на `pw/branches/r1117/Data` (86 877 файлов, 4264,3 МБ), `-j 4`, домашняя машина:

| шаг | время |
|---|---|
| скан `Data` (stat + crc всех файлов) | 6,9 с |
| сборка 39 pile (первый прогон) | 35,9 с |
| пересборка 8 pile после деления | 4,8 с |
| **полная сборка целиком** | **46,5 с** |
| повторный прогон «ничего не изменилось» (43 pile не тронуты) | 12,2 с (из них скан 6,9 с) |
| `verify` с crc всех 86 877 записей | ~50 с |

Результат полной сборки: **43 pile, 86 877 файлов, 4264,3 МБ → 1911,2 МБ (ratio 0,448)**.
Для сравнения: старый пайплайн (`FilePileCompiler.exe`, level 9, 6 прогонов + перемещение
файлов в `_processedFiles`) на тех же данных — минуты, однопоточно. Один поток python
(38,9 МБ/с на сжатии) тоже укладывается в ~110 с, так что требование «не медленнее
оригинала» выполняется с запасом.

Раскладка до первой сборки оценивает упакованный размер по таблице `EST_RATIO_BY_EXT`
(замеренные коэффициенты по расширениям) — из-за неё первые прогоны дают pile чуть больше
цели, после пересборки размеры настоящие.

## 7. Миграция на новый набор (шаги)

1. Собрать и проверить: `./pilepack.sh build --force && ./pilepack.sh verify`
   → `Piles/gamedataNN.pile` (43 контейнера, ~1,9 ГБ).
2. Проверить на стенде: положить `Piles/*.pile` в `Game/Packs/` тестовой установки,
   убедиться, что клиент стартует, лог чист по `PileFileSystem`, битых файлов нет
   (методика — скилл `pw-client`, E2E на tiny10).
3. В канале обновлений (`game-pwc`/`pwc-gitupdates`) удалить старые `*.pile`
   (`git rm Packs/*.pile`), добавить `Packs/gamedataNN.pile`.
4. Установки, где лежат старые `data01…data06.pile`/`epatchNN.pile`/`zpatch_fev.pile`,
   их получат: NanoUpdater снимает untracked-файлы (`main.cpp:748-755`), а `update.sh`
   (`git reset --hard`) — untracked-файлы **не** снимает, там их надо убирать заранее
   (иначе `data06.pile` останется и будет перекрывать новые контейнеры — сортировка
   `PileFileSystem` идёт по убыванию полного пути).
5. `Packs/` в канале обновлений остаётся каталогом для ручных патчей: `zpatch_*`/`epatch_*`
   по-прежнему перекрывают `gamedataNN.pile` (сортировка по убыванию: `z…` > `g…`).

## 8. Тесты

`python3 PilePack/test_pilepack.py` — без сети и клиента: формат-смук (битый тег/версия,
несжатая запись с флагом COMPRESSED, имя с ведущим `'0'`, побайтовая сверка содержимого и
crc), привязка из манифеста (первый прогон → `gamedataNN.pile` подряд, повторный прогон
ничего не пересобирает и не трогает файлы, изменение файла → пересборка только своего pile,
удаление → запись выпадает, но pile остаётся, огрысок pile на диске → замечен и пересобран),
новые/удалённые файлы (новый файл — в последний pile, удалённый не возвращается),
деление oversize-pile по байтам (имена остальных pile не меняются, новая часть — следующий
номер, все части ниже порога), смена цели (раскладка заново, старые pile удалены), переводы
строк (CRLF- и LF-копии дают побайтно одинаковый pile, двоичные файлы — в т. ч. без NUL, но
с одиночными CR — не трогаются), политика и защиты (`ignore_dir`, `exclude`,
`!`-исключение, конфликт имён по регистру — пропускается на ФС без учёта регистра, имя с
ведущим `'0'`).
