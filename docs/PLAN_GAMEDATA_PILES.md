## 1. Как устроено сейчас

### 1.1 Формат pile (обратная совместимость обязательна)

`Src/System/FileSystem/FilePileFormat.h`:

```
FILEPILE_TAG      = 0x656c6950   ("Pile" в файле: 50 69 6c 65)
FILEPILE_VERSION  = 0x00010002   (проверяется загрузчиком, другое значение = pile отбрасывается)
FILEPILE_COMPRESSED = 0x0001

SFilePileTail   <6I: tag, version, filesNumber, stringsOffset, stringsLength, fileIndexOffset
SFilePileEntry  <6I: size, sourceSize, offset, flags, fileNameOffset, crc
```

Раскладка файла (проверено побайтово на `zpatch_fev.pile`, `result.pile`):

```
offset 0            : 4 байта "Pile" (tag, пишется и в начало файла)
offset 4            : блоки данных файлов подряд (первый entry.offset == 4)
stringsOffset       : таблица имён (NUL-терминированные, '/' как разделитель, путь относительно Data)
fileIndexOffset     : filesNumber × 24 байта entry
EOF-24              : tail (не шифруется)
```

* Таблица имён и индекс **обфусцированы SimpleCrypt**: `state = 0; for b: state = (state+83)&0xFF; out = b ^ state` (`Src/System/SimpleCrypt.hpp`). Реализовано и подтверждено рабочим парсером.
* `crc` = **zlib crc32 несжатых** байт (подтверждено: сошлось с `zlib.crc32` при извлечении).
* Сжатие: `compress2(..., level 9)` (`FilePileCompiler.cpp:256`); если `ratio = zipSz/fileSize <= max_comp_ratio` (в пайплайне 0.90) — пишем сжатое и ставим `FILEPILE_COMPRESSED`, иначе пишем raw (`flags = 0`) и загрузчик дополнительно сверяет crc (`FilePileLoader.cpp:162`).
* `-comp_size 1` = `minFileSizeToCompress` (т.е. пробуем сжимать всё > 1 байта).
* Лимиты: `entry.offset` — UInt32 → пайл < 4 ГБ; каждый файл < `fs_piled_file_size_limit` (по умолчанию 256 МБ) и по `size`, и по `sourceSize`. Самый большой файл в Data — `Audio/Asks01_RU.fsb` 83 МБ → запас есть.
* `FilePileLoader::Init` держит `FILE*` открытым всё время жизни процесса; `ReadFileBytes` читает весь блок в heap, `DecompressFile` аллоцирует второй буфер под исходник.

### 1.2 Как клиент выбирает pile

`PileFileSystem::ScanForPiles` (`Src/System/FileSystem/PileFileSystem.cpp:74-113`):

* сканирует `<Base>/Packs/*.pile` (не рекурсивно) **плюс** `<Base>/Data/Localization/<language>/*.pile`;
* сортирует полные пути **по убыванию, регистронезависимо** (`NStr::ICmp(...) > 0`);
* `OpenFile` идёт по списку и берёт **первое** совпадение → более «старшие» по имени pile перекрывают младшие.
  Следствие: `Packs/*` ищутся раньше `Data/Localization/...` (буква P > D), а внутри Packs — `zpatch… > xpatch… > map.pile > data06.pile > … > data01.pile`.
* **pile, не прошедший `Init`, молча пропускается** (вызов callback закомментирован) → клиент теряет контент без ошибки. Вся защита — на стороне сборки.
* `PileFileSystem::GetFiles` возвращает дубликаты имён (в коде `//FIXME`), дедуплицирует `CombinerFileSystem`.

`Src/PW_Client/Game.cpp:1177-1178`: `PileFileSystem` регистрируется **до** `WinFileSystem(<Base>/Data)` → содержимое pile перекрывает loose-файлы в `Data/`.

### 1.3 Текущая сборка (Windows, py2.7)

`prime-world-classic/PW_PackData/PackData.ps1` → `FilePileCompiler/process_data_pile.py` + `FilePileCompiler.exe`:

* `ccl.txt` (54199 строк) — whitelist: все файлы `Data`, чьё расширение есть в `types.txt` (29 расширений: ani, anim, baked_terrain, codes, codes2, coll, dds, heightmap, hlsl, layer_mask, lua, md5, naturemap, objectheight, part, psb, road, shd, shd2, shgrid, skel, skin, stat, swf, tcv_data, ttf, vsb, vtxcolor, watermap, xdb);

* `data01.txt…data06.txt` — разбивка по каталогам/маскам (`data01: +*.xdb +*.md5 -*.txt`, `data02: Audio Buildings Dialog … - *.xdb -*.txt`, `data03: Maps`, `data04: Creeps Critters MiniGames Pets Scripts Server Shaders Social SocialTest Summons Terrain`, `data05: UI`, `data06: Heroes`);

## 2. Находки, которые меняют постановку

### R1. `Data` в исходном репо ≠ то, что видит клиент (главный риск)

Сверка полного baseline (87 116 файлов) с деревом `pw/branches/r1117/Data` (полный
разбор — `DATA_VS_PILES_REPORT.md`):

* **одинаковые** — 61 292 файла (3 658 МБ);
* **«разные» — 25 390, но 25 249 из них (99.4%) отличаются только окончаниями строк**
  (в pile CRLF, в git-блобах LF; `*.xdb` — XML с UTF-8 BOM, поэтому тоже). Настоящих
  расхождений — **141 файл / 150.5 МБ** (79 `.xdb`, 33 `.dds`, 7 `.txt`, 4 `.fsb`,
  4 `.lua`, 1 `.fev`, 13 прочих). Предварительная оценка «16% расхождений» была артефактом CRLF;
* **только в pile — 461 файл / 119.1 МБ** (их нет в `Data`): `UI` 233 (52.4 МБ),
  `Heroes` 34 (41.2 МБ, включая целый каталог `Heroes/Laguna/`), `Summons` 161,
  `Audio` 8 (в т.ч. `Audio/Ping/ping0..5.wav`), `Effects` 2, `Items` 19. Из них 450 —
  только в тест-канале. **Это главный риск: без переноса в `Data` этот контент исчезнет
  с клиентов после удаления старых pile**;
* только в `Data` и попадающих по политике в pile — 178 файлов / 347.6 МБ, из них 171 —
  каталог `Test/` (не пакуется осознанно), остальное (`Debug/`, `deprecated_shaders/`) —
  мусор. «Забытого» контента нет.

Вывод: источник генератора — `Data` исходного репо, но **предварительно** в неё надо
добавить 461 файл из pile и разрешить 141 конфликт вручную.

### R2. fsb уже лежат в pile и работают — требование выполнимо без исключений

В prod и на тест-канале FMOD-банки уже упакованы:

* `epatch07.pile`: `Audio/Ambient.fsb` 34 МБ, `Audio/Heroes.fsb` 22.8 МБ, `Audio/SFX.fsb` 11.5 МБ, `Audio/Asks05_RU.fsb` 2.8 МБ, `Audio/Ping/ping0..5.wav`;
* `epatch01.pile`: `Audio/PrimeWorld.fev`, `Audio/PrimeWorldClassic.fev`, `Audio/SFXnew.fsb`;
* prod: `xpatch07_Aram.pile`, `xpatch08_Aram_Snow.pile`, `xpatch091.pile`, `zpatch_fev.pile` — `Audio/PrimeWorld.fev`.

Механизм: FMOD ходит в движковый FS — `Src/Sound/EventScene.cpp:203 fileOpen(...)` → `RootFileSystem::OpenFile` → сначала `PileFileSystem`. `setMediaPath("\\Audio\\")` (`EventScene.cpp:679`) + ключ pile `Audio/…` совпадают после нормализации. Извлечённый из `zpatch_fev.pile` `PrimeWorld.fev` побайтово равен loose-файлу (md5 `84f91d78bd799fd292e76190108412e5`).

**Цена (не бесплатная):** loose-файлы открываются через mmap (`FileStream_win.cpp:49 CreateFileMapping`, `:55 MapViewOfFile`) — страницы pageable и общие. Файл из pile — приватная heap-память: `ReadFileBytes` (весь сжатый блок) + `DecompressFile` (весь исходник), а FMOD держит банк в `g_soundBanksCache` (hash_map<string, CObj<Stream>>) пока жив процесс. Для `Asks01_RU.fsb` (83 МБ) пик ≈ 40 + 83 МБ. Для x64-клиента с LAA (4 ГБ адресного пространства) это ощутимо → см. вопрос Q3.

Дополнительно: те же fsb сейчас лежат **и в pile, и loose** в `Data/Audio` (425 МБ в prod-канале, 426 МБ в тест-канале, 21 файл / 425 МБ в установке) — loose-копии мёртвый груз (pile перекрывает). **Решение Q3: паковать все fsb/fev/wav без порога**, loose-копии `Data/Audio` из канала обновлений после перехода удаляются.

### R3. Локализация: порядок поиска ломает переопределения

`localisation_files.pile` грузится из `Data/Localization/<lang>/` и в общем отсортированном списке стоит **последним**. Замерено: **398 имён** из локализационного pile одновременно есть в Packs-pile (`gamelogic/talentgroup.tgrp_groups_*_name.txt`, `items/talents/class/*/*.talent_*.txt`) → выигрывает Packs-версия, локализационное переопределение не применяется. Текущий пайплайн этого избегает только трюком `_processedFiles` (override-файлы физически не попадают в `data0X`). **Решение Q8: унификация — отдельный локализационный pile упраздняется**, контент локализации входит в `gamedata*`. Пересечений тогда нет по построению, но теряется переключение языка пачкой: ключи записей относительны корня `Data`, поэтому `ru-RU` и `en-US` дают одинаковые ключи и в один pile не поместятся → в канале остаётся один язык (ru-RU, а `_en`-варианты — отдельными именами). `Data/Localization/<lang>/text.text` (кэш строк, `Game.cpp:1185 TryLoadTextsCache`) остаётся loose-файлом — он читается мимо pile.

### R4. Как именно «удалится старое» (разница Windows и Linux/Wine)

* **NanoUpdater** (`prime-world-classic-nanoupdater-new-repos/PW_NanoUpdater/PW_NanoUpdater/main.cpp:701-755`): `GIT_STATUS_OPT_INCLUDE_UNTRACKED` **без** `INCLUDE_IGNORED` → после `git_reset(HARD)` удаляются untracked-файлы, **но gitignore-файлы выживают**. Т.е. вывод пользователя верен для Windows: `data01…06.pile` (стоят в `.gitignore`) останутся; чтобы их удалить — надо убрать их из `.gitignore` отдельным коммитом.
* **Linux/Wine** (`update.sh` в корне репо): `git fetch --all` + `git reset --hard origin/main` → untracked **не удаляются вообще**. Нужен явный `rm -f Packs/data0*.pile` в `update.sh`.
* Tracked pile (`map.pile`, `xpatch*`, `epatch*`, `result.pile`) исчезнут с клиентов автоматически при удалении из репо.

### R5. Молчаливые отказы загрузки pile

См. §1.2: битый/неподходящий по версии pile просто не грузится. Обязательна build-side валидация (перечитать каждый сгенерированный pile, сверить crc всех записей, `indexEnd + 24 == filesize`) и смоук на клиенте.

### R6. Размер git-репо

Полный набор = ~2.1 ГБ бинарных blob'ов в репо обновлений (сейчас tracked ~640 МБ prod / ~574 МБ тест). Плюс история: каждое изменение файла = новый blob чанка. **Решение Q9: чанки по 50 МБ** (вместо нынешних `epatch*` ~100 МБ и `data03.pile` 440 МБ), LFS не вводим; историю репо обновлений **периодически чистим** (squash/rewrite — процедура отдельная, согласуется с прод-регламентом).

### R7. Что несущественно

29 pile вместо 6: 29 открытых `FILE*`, индекс ~88 809 × 24 Б ≈ 2.1 МБ + строки ~2 МБ, старт — тривиален.

## 3. Проектируемый инструмент `pilepack.py`

### 3.1 Язык и скорость (замеры на реальном Data)

Замер на 162 файлах / 120.6 МБ из `pw/branches/r1117/Data` (python 3, stdlib zlib):

| операция | скорость | ratio |
|---|---|---|
| `zlib.crc32` | 1964 МБ/с | — |
| `zlib.compress(level=9)` | 12.2 МБ/с | 0.531 |
| `zlib.compress(level=6)` | 38.9 МБ/с | 0.533 |

Полная сборка 4.23 ГБ исходников: level 9 ≈ 350 с в один поток, level 6 ≈ 110 с; при 4–8 воркерах (по одному на pile, `concurrent.futures`) — 1–2 минуты. Оригинальный `FilePileCompiler.exe` однопоточный и гоняет данные через 16-МБ буфер по кускам — python не медленнее, а быстрее. **Python 3 + stdlib (zlib, struct, hashlib, os, json, concurrent.futures) — годный выбор, кроссплатформенный.** Уровень сжатия на совместимость не влияет (загрузчик использует `uncompress`), так что level 6 даёт тот же размер в 3 раза быстрее. **Решение Q7: level 6.**

Инкрементальность (как реализовано): скан `Data` — `zlib.crc32` у **всех** файлов каждый
прогон (86 877 файлов / 4,26 ГБ ≈ 7 с). `mtime` в манифесте не хранится: правка «тот же
размер, другие байты» по нему не видна, а стоит дорого. Пересобираются только те pile, у
которых изменилась хотя бы одна запись (или разошёлся индекс на диске с манифестом).

### 3.2 Политика отбора (конфиг)

Семантику текущего пайплайна переносим 1-в-1, иначе клиент потеряет/получит лишние файлы:

* whitelist расширений (`types.txt`, 29 расширений) **плюс** `.fsb/.fev` (унификация, §4)
  и `txt` (локализация, R3); `.wav/.ogg` не добавлены — в `Data` таких файлов нет, а
  политика «что попало, то в pile» потом ловит неочевидные сюрпризы;
* исключённые каталоги: `.svn Debug Templates Test _processedFiles deprecated_shaders`;
  маски: `*.junk`, `*.ignore` и нерусские голосовые банки (`audio/asks0*_EN_TR.fsb`,
  `tutorial_en/tr`, `announcements_en/tr` — аналог `-Exclude` из `PackData.ps1`);
  `Localization` больше **не** исключается;
* каталог `Test/` не пакуется (171 файл / 347.6 МБ только в `Data`);
* правило «`test` в имени» (сегмент каталога или подстрока) действовало **только** при
  извлечении baseline (2 113 записей / 107.1 МБ). В сборку `Maps/test/**` и подобные
  попадают — старый пайплайн их паковал в `data03`, иначе клиент потерял бы контент;
* маски `data01` (`+*.xdb +*.md5`) как отдельная include-политика для корня `Data` не
  нужна: отбор по расширениям единый для всего дерева.

Файл: `PilePack/policy.txt` — один источник правды вместо шести `dataNN.txt`.

### 3.3 Манифест (привязка файлов к слотам)

`PilePack/gamedata_manifest.json` — в **исходном** репо (решение Q6); в `Packs/` его не
класть, иначе он поедет в канал обновлений:

```json
{ "format": 2, "params": {"target_bytes": 52428800, "split_bytes": 62914560, "level": 6,
   "max_ratio": 0.9, "min_compress_size": 1, "prefix": "gamedata", "policy_fingerprint": "…"},
  "piles": [ { "id": 1, "name": "gamedata01.pile", "packed_size": 11448283,
               "files": [ ["Audio/Ambient.fsb", 8577152, 2711085373] ] } ] }
```

* единственный источник правды для членства и порядка; запись — `[ключ, размер, crc32]`,
  по одной на строку, чтобы diff в git оставался читаемым (6,9 МБ, 1,15 МБ gzip);
* `packed_size` на pile → решение «влезет ли слот» не требует чтения pile;
* `policy_fingerprint` (sha256 политики) и параметры сборки: смена любого из них → полный
  пересчёт и пересборка всего;
* режим «восстановить манифест из уже собранных pile» (`--import`) не делался: источник
  истины — `Data`, старые pile не перенимаются. При утере манифеста сборка с нуля даёт другую
  раскладку (контент не теряется, но пересобираются все pile и меняются имена).

### 3.4 Алгоритм сборки

1. **scan**: обход `Data` (или baseline-дерева) + политика → множество `F = {path, size}`.
2. **reconcile** с манифестом:
   * файлы, уже закреплённые за слотом, остаются в своём слоте в прежнем порядке;
   * файлы, удалённые из `Data`, остаются в манифесте до ближайшей пересборки своего pile,
     при пересборке запись выпадает — привязка не рвётся, новый файл в этот слот не придёт
     (требование 2);
   * новые файлы дописываются в **последний** слот, чей `packed` < target; если такого нет — создаётся новый `gamedataNN+1`;
   * файлы, отсутствовавшие в манифесте и не прошедшие политику, логируются отдельным списком (защита от «забыли каталог» — аналог leftovers).
3. **diff**: сравнить `crc32` файлов слота с манифестом → множество «грязных» слотов; сжимаем и пишем только их (`--all` форсирует полную пересборку, `--only gamedata03,gamedata07` — выборочную).
4. **split**: если собранный слот > `split_bytes` (60 МБ при таргете 50 МБ) — список файлов слота делится **по байтам исходников** пополам (решение Q5), вторая половина уходит в новый слот, последующие слоты сдвигаются (перенумерация, как просил пользователь). Контент неизменных слотов побайтово совпадает → git видит переименование без докачки объектов.
5. **write** (детерминированно): порядок = порядок в манифесте; фиксированный уровень zlib; правило ratio как у компилятора (`ratio ≤ 0.90` → сжать + флаг, иначе raw); имена с `/`, NUL-терминированные; SimpleCrypt на строки и индекс; tail в конец. Детерминизм критичен: иначе каждый прогон даёт новые blob'ы = полная докачка.
6. **verify**: перечитать каждый записанный pile — число записей, crc каждого файла, `indexEnd + 24 == filesize`, отсутствие дублей имён внутри и пересечений с `localisation_files.pile`.
7. **prune**: удалить из выходного каталога `*.pile`, которых нет в манифесте.

CLI:

```
pilepack.py build   --data <Data|baseline> --out <Packs> --policy pile_policy.txt
                    --manifest PW_PackData/gamedata_manifest.json [-j 8] [--all] [--only …]
                    [--dry-run] [--split-at 60000000] [--target 50000000]
pilepack.py verify  --out <Packs>
pilepack.py import  --out <Packs> --manifest <…>      # восстановить манифест из pile
pilepack.py extract --pile <f.pile> [--name <path>] [-o <dir>]   # отладка
```

Полезный побочный продукт: `extract`/`verify` уже написаны и работают (парсер с проверкой crc использовался для замеров §1.4) — их стоит положить в `PW_PackData/` как инструмент отладки.

## 4. Ответ на требование «fsb в pile»

Работает — уже используется в проде и на тест-канале (R2). Подтверждено кодом: FMOD открыт через `RootFileSystem::OpenFile` (`Src/Sound/EventScene.cpp:216`, `Src/Sound/SoundScene.cpp:283`), а `PileFileSystem` зарегистрирован раньше `WinFileSystem(<Base>/Data)` (`Src/PW_Client/Game.cpp:1177-1178`) → запись из pile приоритетнее loose-файла; `FilePileStream` поддерживает произвольный `Seek` (весь файл в памяти), так что случайные чтения FMOD корректны. **Решение Q3: все fsb/fev/wav пакуем, порога нет**, `Data/Audio/*.fsb` из доставки уходят. Обязательный смоук: заход в лобби + бой + проигрывание звуков (ошибка FMOD `Cannot load events from file "%s" referenced from object "%s"` = банк не найден/не прочитан).

## 7. Принятые решения

* **Q1 — вход генератора:** `Data` исходного репо. Сначала сравнить извлечённое дерево с `Data` (сверка сделана, §2 R1), ничего не строить до отчёта; в итоге объединить данные и собирать из `Data`.
* **Q2 — объём:** весь клиентский набор (4.31 ГБ исходников → ≈42 pile); старые `data0X`/`epatch*`/`xpatch*`/`map.pile`/`result.pile` **удаляются**.
* **Q3 — fsb:** класть в pile все (унификация, исключений для fsb не будет).
* **Q4 — пороги:** таргет **50 МБ** на packed-размер pile (вместо 70/80); порог split — 60 МБ (пропорция от исходных 80→95, уточнить).
* **Q5 — split:** по байтам исходников.
* **Q6 — манифест:** в исходном репо (`PW_PackData/gamedata_manifest.json`).
* **Q7 — сжатие:** zlib level 6.
* **Q8 — локализация:** унификация, отдельно локализацию не храним (контент входит в `gamedata*`).
* **Q9 — размер git:** чанки по 50 МБ (это уменьшает историю), историю репо обновлений периодически чистим; LFS не вводим.
