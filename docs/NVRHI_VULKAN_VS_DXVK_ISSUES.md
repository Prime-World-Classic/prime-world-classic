# Сравнение RenderDoc-капч NVRHI(Vulkan) ↔ DXVK: найденные проблемы

Разбор двух капч одного и того же клиента (D3D9-слой `d3d9`), сделанный поштучно по
событиям. Цель — найти события, которые в NVRHI/Vulkan приводят к расхождению
картинки, а в DXVK — нет.

# Проблема 1 (критическая). Карта теней рисуется viewport/scissor 1024×768 вместо 2048×2048

Заполняется ровно **1/4 площади** карты теней (по X — 1/2, по Y — 768/2048 = 3/8),
остальные 3/4 карты в кадре NVRHI **не записываются никогда**. DXVK пишет всю карту.

## События Vulkan

Проход карты теней: `vkCmdBeginRendering` area=`2048x2048` offset=`(0,0)`,
аттачменты — color `view#36431 → img#36424`, depth `view#36432 → img#36422`.
Проходов несколько (`passn` 48, 62, 74, …), суммарно **107 `vkCmdDrawIndexed`,
400 767 индексов, ev54 … ev999**. Состояние на все 107 одинаковое:

```
ev54  vkCmdDrawIndexed indexCount=978 instanceCount=1 firstIndex=0 vertexOffset=0
      pass ev… area=2048x2048 off=(0,0)
      VP (0, 768, 1024, -768)  SC (0, 0, 1024, 768)      <-- ОШИБКА: размер чужой цели
```

Последовательность всех `vkCmdSetViewport`/`vkCmdSetScissor` кадра (9 пар) —
**ни одна не 2048×2048**:

```
VP(0,205,205,-205)   SC(0,0,205,205)    -> draw#0   ev25   img#29351
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#2   ev54   img#36424  (КАРТА ТЕНЕЙ)
VP(0,256,256,-256)   SC(0,0,256,256)    -> draw#227 ev1883 img#182
VP(0,384,512,-384)   SC(0,0,512,384)    -> draw#229 ev1907 img#190
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#318 ev2435 img#170
VP(0,192,256,-192)   SC(0,0,256,192)    -> draw#347 ev2797 img#206
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#350 ev2830 img#172
VP(0,201,200,-201)   SC(0,0,200,201)    -> draw#560 ev4712 img#23087
VP(0,768,1024,-768)  SC(0,0,1024,768)   -> draw#569 ev4762 img#3607
```

То есть viewport ставится под каждую цель (205², 256², 512×384, 256×192,
200×201, 1024×768) — **кроме** 2048². Перед ev54 действует значение,
поставленное для прохода 205×205→1024×768, и оно переносится на проход карты теней.

### Ресурсы (состояние на ev54…ev999)

- color: `view#36431` → `img#36424` `VK_FORMAT_B5G6R5_UNORM_PACK16` 2048×2048,
  mips=1 layers=1, layout `COLOR_ATTACHMENT_OPTIMAL`,
  usage `TRANSFER_SRC|TRANSFER_DST|SAMPLED|COLOR_ATTACHMENT`,
  load=`LOAD`, store=`STORE`, **`colorWriteMask=0`** (в цвет не пишут)
- depth: `view#36432` → `img#36422` `VK_FORMAT_D24_UNORM_S8_UINT` 2048×2048,
  layout `DEPTH_STENCIL_ATTACHMENT_OPTIMAL`,
  usage `TRANSFER_SRC|TRANSFER_DST|SAMPLED|DEPTH_STENCIL_ATTACHMENT`,
  load=`LOAD`, store=`STORE` — **без clear'а**, см. Проблему 3
- pipeline: 107 рисунков распределены по **22 разным pipeline** (самый частый
  `pipe#37233` — 23 рисунка, далее `37235`×13, `37265`×13, `37237`×12, …).
  Статика `pipe#37233` (первый рисунок ev54): topo=`TRIANGLE_LIST`,
  cull=`BACK`, front=`CCW`, fill=`FILL`, `dtest=1 dwrite=0 dcmp=LESS_OR_EQUAL`,
  blend выключен, `samples=1`, `vbind=4B;32B`,
  `vattr=R32G32B32F@0;…;R16G16_SINT@0`
- VB/IB: `buf#23759@47255680` (+`@24223232`, `@24335936`), `buf#144@0` ×5,
  `buf#36435@0`; IB `buf#23759@47277312` `UINT32`
- цель `img#36422` имеет `SAMPLED` — карта выбирается шейдером сцены как текстура

## События dxvk

Одиночный проход `vkCmdBeginRendering` area=`2048x2048` offset=`(0,0)`
(`passn` 29), **107 `vkCmdDrawIndexed`, 400 767 индексов, ev53 … ev522** —
тот же набор рисунков, что и у NVRHI (мультимножество `indexCount` совпадает 1:1):

```
ev53  vkCmdDrawIndexed indexCount=978 instanceCount=1
      pass ev… area=2048x2048 off=(0,0)
      VP (0.5, 2048.5, 2048, -2048)  SC (0, 0, 2048, 2048)   <-- верный размер цели
```

Вызов, который в NVRHI отсутствует:

```
vkCmdSetViewportWithCount  x=0.5 y=2048.5 width=2048 height=-2048
vkCmdSetScissorWithCount   x=0   y=0    width=2048 height=2048
```

### Ресурсы (состояние на ev53…ev522)

- color: `view#12891` → `img#11920` `VK_FORMAT_R5G6B5_UNORM_PACK16` 2048×2048,
  layout `GENERAL`, usage `TRANSFER_SRC|TRANSFER_DST|COLOR_ATTACHMENT`
  (**без `SAMPLED`**), load=`LOAD`, store=`STORE`, `colorWriteMask=0`
- depth: `view#12892` → `img#11914` `VK_FORMAT_D24_UNORM_S8_UINT` 2048×2048,
  layout `GENERAL`, usage `…|SAMPLED|DEPTH_STENCIL_ATTACHMENT`,
  **load=`CLEAR` value=`(1,0,0,0)`**, store=`STORE`
- VB/IB: DXVK-«Global buffer» `buf#3381` (256 МиБ), индексы `UINT32`
- глубина и трафарет — динамическое состояние (`DYNAMIC_STATE_DEPTH_*`,
  `DYNAMIC_STATE_STENCIL_*` в pipeline), значения задаются
  `vkCmdSetDepthTestEnable`/`…CompareOp`/`…WriteEnable` (по 28 вызовов)

## Возможная причина возникновения проблемы

NVRHI-слой D3D9 **не перевыставляет viewport/scissor при смене цели рендера на
2048×2048** (surface карты теней): он выставляет viewport под остальные цели
(205², 256², 512×384, 256×192, 200×201, 1024×768), а для прохода карты теней
использует то, что осталось от предыдущего прохода — 1024×768. Клиент при этом
`SetViewport(0,0,2048,2048)` вызывает: в DXVK-капче он доходит до Vulkan как
`vkCmdSetViewportWithCount(0.5, 2048.5, 2048, -2048)` ровно перед ev53.

Следствие: геометрия теней проецируется в прямоугольник 1024×768 внутри
2048²-изображения (сжатие 2× по X и 2.67× по Y относительно того, что делает
DXVK), а 3/4 карты остаётся нетронутой.

Проверка гипотезы выполнена так: viewport поправлен на размер цели, снята
повторная капча (`pw_frame2920`). Дефект карты закрыт (viewport 2048² появился),
но **к полосам на скриншоте это отношения не имеет** — полосы остались; разбор
полос — в начале документа и в `docs/PLAN_NVRHI.md`.

# Проблема 2. Полувитковый сдвиг viewport (D3D9 half-texel) не применяется нигде

## События Vulkan

Во **всех** проходах viewport без смещения:

```
VP(0,   205,   205, -205)   VP(0,   768,   1024, -768)   VP(0,   256, 256, -256)
VP(0,   384,   512, -384)   VP(0,   192,   256,  -192)   VP(0,   201, 200, -201)
```

## События dxvk

Во всех проходах (кроме финального blit-а) смещение +0.5 по X и Y:

```
VP(0.5, 205.5, 205, -205)   VP(0.5, 768.5, 1024, -768)   VP(0.5, 256.5, 256, -256)
VP(0.5, 384.5, 512, -384)   VP(0.5, 192.5, 256,  -192)   VP(0.5, 201.5, 200, -201)
```

Пара для примера: NVRHI `ev4558` (цель `img#172`, UI) `VP=(0,768,1024,-768)` ↔
DXVK `ev1948` (цель `img#246`, UI) `VP=(0.5,768.5,1024,-768)`.

### Ресурсы

Те же цели, что в Проблеме 1/3: `img#172`↔`img#246` BGRA 1024×768,
`img#170`↔`img#244` BGRA 1024×768 и т. д.; различается только прямоугольник
viewport.

## Возможная причина

D3D9 использует семплирование по центрам пикселей, и DXVK при трансляции
viewport добавает half-texel bias (+0.5), как того требует D3D9→Vulkan.
NVRHI этого смещения не добавляет. Следствие — сдвиг всей растеризации на полпикселя:
размытие/«мерцание» при билинейной фильтрации и текстурах, сдвиг краёв UI на
пиксель. К полосам из Проблемы 1 это отношения не имеет (период полос ~20 px),
но это систематическое расхождение A/B по всему кадру.

# Проблема 3. Утерян load-op CLEAR: все аттачменты LOAD, явных clear'ов 7 на кадр

## События Vulkan

На каждый из 467 проходов все аттачменты — `ATTACHMENT_LOAD_OP_LOAD` /
`STORE`. Единственные clear'ы — отдельные команды:
`vkCmdClearColorImage` ×3, `vkCmdClearDepthStencilImage` ×4 (например clear
`img#36422` выполняется вне прохода карты теней).

```
ev54 pass: C view#36431 img#36424 LOAD/STORE ; D view#36432 img#36422 LOAD/STORE
```

## События dxvk

Clear задаётся самим load-op прохода:

```
ev53 pass: C view#12891 img#11920 LOAD/STORE
           D view#12892 img#11914 CLEAR value=(1,0,0,0) /STORE
           S view#12892 img#11914 CLEAR value=(1,0,0,0) /STORE
ev570 pass (цель сцены): C img#244 CLEAR (0,0,0,0) ; D/S img#240 CLEAR (1,0,0,0)
```

Всего в DXVK: 3 color-CLEAR + 4 depth-CLEAR + 3 stencil-CLEAR в load-op,
ноль отдельных clear-команд.

### Ресурсы

Одни и те же изображения (`img#36422`↔`img#11914`, `img#170`↔`img#244`,
`img#166`↔`img#240`), different — способ инициализации.

## Возможная причина

NVRHI всегда ставит `LOAD`, а сброс выполняет отдельными
`vkCmdClearColorImage`/`vkCmdClearDepthStencilImage` вне проходов. Там, где
DXVK гарантированно обнуляет цель перед первым рисунком (карта глубины теней —
`(1,0,0,0)`, сцена — `(0,0,0,0)`), NVRHI приносит старое содержимое. В
сочетании с Проблемой 1 это означает, что 3/4 карты теней, не закрытые
растеризацией, содержат **старые данные**, а не «пустую» глубину.

# Проблема 4. Проход рендера открывается на каждый рисунок (467 против 33)

## События Vulkan

467 пар `vkCmdBeginRendering`/`vkCmdEndRendering`; внутри, как правило, **один**
`vkCmdDraw*`, между проходами — `vkCmdPipelineBarrier2` и `vkCmdUpdateBuffer`.
Пример подряд идущих: `ev1587 BeginRendering → ev1592 DrawIndexed → ev1593
EndRendering → ev1594 barrier → ev1595 UpdateBuffer`. Всего
`vkCmdPipelineBarrier2` = **1214**.

## События dxvk

33 прохода, в каждом пачка рисунков (например `passn` 29 — 107 рисунков карты
теней, `passn` со start `ev3232` — 89 рисунков UI). Всего
`vkCmdPipelineBarrier2` = **46**.

### Ресурсы

Те же цели; различие — только в гранулярности проходов и числе переходов
layout/barrier.

## Возможная причина

D3D9-слой NVRHI считает каждое изменение состояния границей subpass. Следствие —
полный load/store больших целей (2048², 1024²) на каждый рисунок и 26× больше
барьеров. Это не только потеря производительности: при `LOAD`-повсеместности
(Проблема 3) каждый такой проход — ещё одна возможность принести старое
содержимое вместо clear'а.

- pipeline `13196`/`13199`: `dtest=0 dwrite=0 dcmp=NEVER`, cull=`NONE`,
  blend `ONE / ONE_MINUS_SRC_ALPHA`, stencil cmp=`NEVER`,
  `vattr = R32G32B32F@0 (позиция); B8G8R8A8U@12 (diffuse); B8G8R8A8U@16
  (specular); R32G32B32A32F@20 (texcoord)`, vbind stride динамический
- это **неосвещённая, всегда проходящая по глубине, альфа-блендевая геометрия**
  (декори/эффекты/наложения)

## Возможная причина

Двусмысленно, требует проверки:

1. **Разница моментов съёмки.** Кадры 2314 и 9105 — не один и тот же момент
   (см. Проблему 6: число инстансов эффектов различается). Эффектная геометрия
   могла отсутствовать в кадре NVRHI.
2. **Потеря рисунков в NVRHI.** Косвенный признак: во всём кадре NVRHI **нет ни
   одного pipeline с вершинной декларацией этого блока**
   (`pos3@0 + BGRA@12 + BGRA@16 + RGBA32F@20`, stride 36) — при 109 pipeline и
   25 различных декларациях. Но pipeline создаётся лениво, так что это
   доказательством не является.

Диагноз возможен только на **синхронной паре** (одинаковый игровой момент,
одинаковая поза камеры, одинаковый HP). Индикатор: появляется ли в NVRHI
pipeline с декларацией `pos3@0;BGRA@12;BGRA@16;RGBA32F@20` и рисунки с
`indexCount ∈ {3846, 801, 1728, 3444, 2178, 567, 2490, 1776, 1200, 1620, 684}`.

# Проблема 7. Лишние проходы NVRHI без пары в DXVK

## События Vulkan

1. `ev1907 vkCmdDrawIndexed cnt=6` в цель `img#190` (BGRA 512×384,
   `PW tex 512x384`), VP `(0,384,512,-384)`. У NVRHI **две** цели 512×384:
   `img#186` (88 рисунков) и `img#190` (1 рисунок).
2. `ev25` и `ev35` — два рисунка в **две** цели 205×205 (`img#29351`, `img#29347`).

### Ресурсы

`img#190` BGRA 512×384, load=`LOAD`, depth-аттачмента нет,
`dcmp=LESS dtest=0`; VB — маленький буфер (96 Б), один quad.
`img#29347`/`img#29351` BGRA 205×205, по одному quad-рисунку.

## События dxvk

1. **Пары нет.** У DXVK одна цель 512×384 (`img#251`, 88 рисунков, старт `ev1256`).
2. **Пары нет** для второго 205×205: у DXVK одна цель `img#5055`, один рисунок
   `ev23 cnt=6`, VP `(0.5,205.5,205,-205)`.

## Возможная причина

NVRHI создаёт дополнительные поверхности того же размера и рисует в них quad
(помощник загрузки/копии, либо вторая поверхность, которую DXVK переиспользует).
Либо снова разница моментов. Требует синхронной пары; само по себе на полосу
влиять не может (цели 512×384 и 205×205 в финальный композит не входят).

# Проблема 8. Финальный композит: разная длина цепочки и разный формат swapchain

## События Vulkan

Один полный экран: `ev4762 vkCmdDrawIndexed cnt=6`,
`C view → img#3607` (**B8G8R8A8_UNORM**), load=`LOAD`,
VP `(0,768,1024,-768)`, pipeline `37666`. Источник — `img#172` (UI-цель).
`vkQueuePresentKHR` без дополнительного blit-а.

### Ресурсы

`img#3607` — swapchain image, формат `B8G8R8A8_UNORM`; читаемая цель `img#172`
BGRA 1024×768, 204 рисунка до этого.

## События dxvk

Два шага:

```
ev3837 vkCmdDrawIndexed cnt=6  C img#199 (BGRA_UNORM) LOAD   VP(0.5,768.5,1024,-768)  pipe#11716
ev3863 vkCmdDraw       cnt=3   C img#392 (BGRA_**SRGB**) DONT_CARE  VP(0,0,1024,768)  pipe#420
```

`vkCmdBlitImage2` ×1 в кадре.

### Ресурсы

`img#199` BGRA 1024×768 (промежуточная), `img#392` swapchain
**B8G8R8A8_SRGB**. По инвентарю изображений: у DXVK 3 изображения
`B8G8R8A8_SRGB` и 4 `R16G16B16A16_SFLOAT`, у NVRHI — **ни того ни другого**
(все BGRA у него UNORM).

## Возможная причина

DXVK ведёт present через отдельный blit в sRGB-swapchain (аппаратное
линейно→sRGB преобразование на записи), NVRHI рисует прямо в UNORM-swapchain
без преобразования и без Y-инверсии в последнем проходе (`VP(0,0,1024,768)` у
DXVK-блина против `VP(0,768,1024,-768)` у NVRHI). Если где-то в цепочке кадр
оказывается в линейном пространстве, форматы дают разную яркость/гамму.
К полосам отношения не имеет, но это расхождение цвета A/B, которое надо
зафиксировать до визуальной сверки кадров.

# Проблема 9. Формат color-аттачмента карты теней: B5G6R5 против R5G6B5

## События Vulkan

`view#36431 → img#36424` `VK_FORMAT_B5G6R5_UNORM_PACK16` 2048×2048.

## События dxvk

`view#12891 → img#11920` `VK_FORMAT_R5G6B5_UNORM_PACK16` 2048×2048.

## Возможная причина

Неверный маппинг `SurfaceFormat::bfR5G6B5` в NVRHI-слое (каналы R и B
переставлены). В этом кадре **визуально не влияет**: `colorWriteMask=0` в обоих
капчах, то есть в цвет карты теней не пишут, а выбирается шейдером depth-изображение
(`img#36422` / `img#11914`, оба с `SAMPLED`). Править всё равно нужно — при
любом сценарии, где цвет карты теней используется, каналы поедут.

---

# Что различается, но дефектом не является

Чтобы не гонять эти пункты повторно:

- **Depth/stencil-аттачмент отсутствует у 198 рисунков NVRHI** (`img#172` — 173,
  `img#23087` — 9, `img#170` — 6, прочие — по 1–2), там где DXVK всегда несёт
  `D#213`/`S#213`. Проверено по pipeline: у **всех** этих рисунков
  `dtest=0 dwrite=0 stest=0` — глубина не нужна, аттачмент правомерно опущен.
- **109 pipeline у NVRHI против 70 у DXVK** — NVRHI запекает состояние в
  pipeline, DXVK делает depth/stencil/cull/viewport динамическим
  (`DYNAMIC_STATE_*` + 96×`vkCmdSetStencilOp`, 83×`vkCmdSetCullMode`,
  28×`vkCmdSetDepthTestEnable`). Сравнивать надо **эффективное** состояние на
  рисунке, а не статику pipeline.
- **Способ записи дескрипторов**: NVRHI — 123 статических set'а и 525
  `vkCmdBindDescriptorSets` + 711 `vkCmdUpdateBuffer`; DXVK — 322 364
  `vkGetDescriptorEXT` + `vkCmdSetDescriptorBufferOffsets2EXT`. Разные
  стратегии, не расхождение.
- **`img#36424` имеет `SAMPLED`, `img#11920` — нет.** Разница в флагах создания,
  при `colorWriteMask=0` без последствий.
