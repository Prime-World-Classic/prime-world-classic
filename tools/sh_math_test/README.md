# sh_math_test — оракул D3DX-математики (этап 1 плана `docs/PLAN_NVRHI.md`)

Зачем: клиент зовёт из `d3dx9_43.dll` две функции — `D3DXSHEvalDirectionalLight`
(`Render/SHCoeffs.cpp`) и `D3DXMatrixInverse` (`Render/ShadowManager.cpp`).
Перед заменой на свою реализацию нужно знать **точные** константы и порядок
операций D3DX, иначе молча поедут тени/свет. Этот прогоняемый тест и есть
измерение: он печатает то, что реально выдаёт настоящая MS-библиотека, и
сравнивает кандидата.

```sh
./run.sh          # сборка cl 14.44 под Wine + запуск
DXRED=/path/to/x64 ./run.sh   # если распаковка x64-редистрибьюла в другом месте
```

Нужен **x64** `d3dx9_43.dll` из DirectX End-User Runtime (JUN2010,
`JUN2010_d3dx9_43_x64`): в дереве лежит только x86-версия
(`Vendor/DirectX/Lib/x64/d3dx9.lib` — импортная либа, а DLL в
`Vendor/DirectX/bin/` — 32-битная). Wine по умолчанию подставляет **свой**
`d3dx9_43` (builtin), у которого своя математика — поэтому в `run.sh` стоит
`WINEDLLOVERRIDES=d3dx9_43=n` (грузить нативный MS DLL рядом с exe).

## Что показала D3DX (x64, JUN2010)

`D3DXSHEvalDirectionalLight(order=3, dir, R, G, B, pR, pG, pB)` заполняет 9
коэффициентов на канал по базису **ортонормированных вещественных сферических
гармоник**, порядок индексов — как в D3DX:

| i | базис | множитель |
|---|---|---|
| 0 | 1 | `c0` |
| 1 | y | **−**`c1` |
| 2 | z | `c1` |
| 3 | x | **−**`c1` |
| 4 | xy | `c2` |
| 5 | yz | **−**`c2` |
| 6 | (3z²−1)/2 | `c3` |
| 7 | xz | **−**`c2` |
| 8 | x²−y² | `c4` |

Знак: у `x` и `y` отрицательный, у `z` положительный — D3DX работает в левой
системе координат. Отношения констант: `c1/c0 = √3`, `c3/c0 = √5`,
`c2/c0 = √15`, `c4/c0 = √15/2`.

Константы **битами** (сняты подбором направлений, при которых моном ровно 1,
т.е. без округления на умножение):

```
c0 = 0x3F558751  (0.834096014)
c1 = 0x3FB8EBD2  (1.444696665)
c2 = 0x404EBF89  (3.230440378)   # <-- не 3.23043990: ошибка литерала стоила 4e-6
c3 = 0x3FEEBB70  (1.865095139)
c4 = 0x3FCEBF88  (1.615220070)
```

Реализация линейна по интенсивности (`f(k·d) = k·f(d)` — проверено) и не
зависит от порядка скобок: три варианта ассоциации
`(c*comp)*I`, `c*(comp*I)`, `(c*I)*comp` дают одинаковое расхождение.

## Измеренное расхождение кандидата с D3DX

400 случайных единичных направлений, случайная интенсивность 0.1…3.8:

```
maxAbs = 9.5e-7      maxRel = 4.3e-6
```

`maxAbs` — это ~1 ULP на величинах порядка 1…6. `maxRel` больше только там, где
коэффициент близок к нулю (член `(3z²−1)/2` при z²≈1/3 — вычитание близких
чисел); в относительном выражении это артефакт деления на малое число, абсолютная
ошибка та же ~1e-6.

Вывод: замена `D3DXSHEvalDirectionalLight` своей реализацией **безопасна по
точности** (погрешность на уровне последнего бита float, визуальных изменений
не даёт). Дополнительный плюс: уходит Wine-фолбэк
(`Compatibility::IsRunnedUnderWine()`), который пишет только DC-член и при этом
**меняет каналы местами** (`GCoeffs()[0]=B; BCoeffs()[0]=G`) — с своей
реализацией под Wine и под нативным Windows считается одно и то же.

## `D3DXMatrixInverse`

Тест печатает детерминант и обратную матрицу для четырёх случаев
(общая, масштаб, перенос, поворот+сдвиг) — это эталон, с которым надо
сравнивать свою реализацию (кофакторное разложение D3DX), потому что у
`ShadowManager.cpp` (3 вызова) обратная матрица уходит в матрицу теней и
разница в последнем бите видна как дрог границ теней.


## Раздел «математика»: что показал замер (2026-10-13)

`sh_math_test` дополнен разделом `MathSection` (1000 случайных входов на функцию,
кандидат против настоящей `d3dx9_43.dll` x64) и разделом `FormulasSection` /
`ProbeSection` (фиксированные входы, по которым читается фактическая формула).

Итог по кандидатам (скалярные реализации, `/O2`, x64):

| функция | max\|d\| | не совпало побитово | вывод |
|---|---|---|---|
| `D3DXMatrixTranspose` | 0 | 0/16000 | **побитово** |
| `D3DXMatrixTranslation` | 0 | 0/16000 | **побитово** |
| `D3DXMatrixMultiply` | 3.8e-06 | 2385/16000 | формула верна, разное порядок-ассоциация |
| `D3DXMatrixInverse` | 2.3e-05 | 8640/16000 | формула верна (на хорошо обусловленных входах) |
| `D3DXMatrixLookAtLH` | 1.1e-05 | 5768/16000 | формула верна |
| `D3DXMatrixOrthoLH` | 1.2e-07 | 253/16000 | формула верна |
| `D3DXMatrixOrthoOffCenterLH` | 3.8e-06 | 799/16000 | формула верна |
| `D3DXMatrixPerspectiveLH` | 1.9e-06 | 418/16000 | формула верна |
| `D3DXVec3Normalize` | 1.8e-07 | 1161/3000 | ни `x*inv(sqrt)`, ни `x/sqrt` не совпадают побитово |
| `D3DXVec3TransformCoord` | 3.1e-05 | 2790/3000 | обязано быть деление на `w` (иначе расхождение ~1e4) |

Что это значит на практике:

1. **Формулы D3DX нельзя брать «по документации»** — DLL считает не так, как
   обычно пишут в справочниках: `OrthoLH` — масштаб `2/w`, `2/h` (не `1/w`);
   `PerspectiveLH` — `_33 = zf/(zf-zn)` и `_43 = -zf*zn/(zf-zn)` (без множителя
   2); `OrthoOffCenterLH` — порядок параметров `(l, r, b, t)`, а не `(l, b, r, t)`
   (в заголовке именно так, но по памяти легко перепутать, и тогда матрица
   получается осмысленной, но неверной). Сначала снимать формулу пробами, потом
   писать кандидат.
2. **`Vec3TransformCoord` без перспективного деления на `w` даёт расхождение в
   ~1e4** — это не «округление», это другая функция.
3. **Мерить `Inverse` на случайных матрицах бессмысленно**: детерминант
   случайной 4x4 близок к нулю, и расхождение в последнем бите усиливается до
   единиц. В тесте `Inverse` мёрится на `поворот*сдвиг` — как в клиенте.
4. **Побитово совпадают только `Transpose` и `Translation`.** Остальные
   расходятся на 1-2 ULP (доли процента компонентов) — DLL собрана с SSE и
   другой ассоциацией сложений. Добиться побитового совпадения можно только
   повторив последовательность DLL (по дизассемблеру), либо приняв однократное
   изменение чисел.

Вывод для плана: замена D3DX-математики — не механическая. Перед заменой каждой
функции нужно решить, допускаем ли мы однократное изменение чисел (своя
реализация детерминирована на всех CPU при `/fp:strict`, но отличается от
`d3dx9_43.dll`), и если да — менять все клиенты атомарно одной версией.
